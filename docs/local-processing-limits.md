# 本地处理上限与实测边界

2026-11-14，用户要求实跑合理边界，随后决定仅提高线稿和已验证提取，不开放 SVG 试验档。

## 本次生效范围

| 路线 | 上限 | 说明 |
| --- | --- | --- |
| 本地模型线稿 `method=model` | 25,000,000 像素 | 原尺寸重叠分块推理；不扩大已有上传/解码限制 |
| Otsu 前景提取 | 4,000,000 像素 | 已通过真实队列、独立 worker 与产物发布 |
| 其他普通本地处理、直接矢量化 | 保持 1,000,000 像素 | 不将单项测试结论推广到未验证算法 |
| 组合/批次的彩色矢量工作副本 | 保持 250,000 像素 | 普通直接矢量入口仍沿用既有 1 MP 接入限制 |
| LeftRefill 修复 | 512×512 | 固定模型输入，不随线稿上限变化 |

`GET /api/v1/health` 的 `limits` 提供 `model_lineart_pixels`、`threshold_pixels`、`working_pixels`、`color_vector_pixels` 和 `working_copy_pixels`。工作副本需要用户明确选择，保留原图与缩放来源。预设允许只输出 PNG；如同时开启蒙版、SVG 或平铺，显式副本还需满足这些环节的较低限制。不填副本参数不会隐式缩图，超限任务会保留已有结果并给出错误。

## 实测依据

设备为 Ryzen 9 8945HX、32 GiB RAM、RTX 5070 Laptop 8 GiB。测试使用独立受限子进程，单进程 6 GiB 内存保护，矢量探测最多 60 秒、模型探测最多 90 秒，重任务串行执行。没有云端调用、下载、依赖升级或修改权重。

GPU 线稿使用当前 TGS 模型和合成纹样，输入输出尺寸一致：

| 像素 | 算法及加载耗时 | 进程峰值 RSS |
| --- | --- | --- |
| 1 MP | 7.95 秒 | 1,227 MiB |
| 4 MP | 7.51 秒 | 1,268 MiB |
| 9 MP | 12.56 秒 | 1,373 MiB |
| 16 MP | 19.77 秒 | 1,519 MiB |
| 25 MP | 29.60 秒 | 1,708 MiB |

这些模型任务的 CUDA 分配峰值约 431 MiB、保留峰值约 570 MiB，均不含其它程序的显存。模型按 512 像素、步长 256 原尺度分块，25 MP 方图约 361 块。4 MP Otsu 单算法测试通过；另有真实 HTTP → worker → 4 MP PNG 发布测试通过。

矢量化的像素数不能单独预测内存：固定布局的简单纹样在 4 MP 下彩色/单色都通过（约 8 秒、1.6 GiB RSS），而含固定密度细线、花瓣、孔洞和色界的密集纹样在 1 MP 下均发生 Rust 内存分配失败；密集彩色 4 MP 同样失败，之后未继续升档。

追加的低档定位：密集彩色 250k 通过（2.61 秒、Private Usage 峰值约 1.04 GiB），490k 通过（9.31 秒、约 3.55 GiB）；密集单色 250k 通过（1.55 秒、约 0.64 GiB）。失败进程没有峰值采样，不能断言其恰好触及 6 GiB。490k 测量期间全机提交内存峰值约 30.05/64.80 GiB，没有全机提交内存耗尽迹象。

本轮没有固定真实纹样集的保真验收；更大的输入不等于更高准确率或更好的 SVG 可编辑性。原始验证脚本与 JSON 位于 Git 忽略的 `storage/validation/pixel-limit-review/`，不加入源码提交。
